> Homfunctor examples from computer science

In category theory, a **Hom-functor** turns morphisms into sets of morphisms. For an object $A$, there are two standard forms:

$$
\mathrm{Hom}(A,-):\mathcal C\to\mathbf{Set}
$$

and

$$
\mathrm{Hom}(-,A):\mathcal C^{op}\to\mathbf{Set}.
$$

Here are concrete computer-science examples.

## 1. The Reader functor

In a category of types and functions,

$$
\mathrm{Hom}(R,X)=R\to X.
$$

Fixing $R$ gives the familiar Reader functor:

```haskell
type Reader r a = r -> a

fmap :: (a -> b) -> Reader r a -> Reader r b
fmap f reader = f . reader
```

For example:

```haskell
lengthOfName :: User -> Int
lengthOfName = length . userName
```

The functor maps an output transformation `String -> Int` over a computation `User -> String`.

Thus:

$$
\mathrm{Reader}\ R = \mathrm{Hom}(R,-).
$$

---

## 2. Continuations and predicate transformers

Fix the result type $R$ in the other argument:

$$
\mathrm{Hom}(X,R)=X\to R.
$$

A function $f:X\to Y$ induces

$$
\mathrm{Hom}(Y,R)\to\mathrm{Hom}(X,R)
$$

by precomposition:

$$
k\mapsto k\circ f.
$$

In code:

```haskell
contramap :: (x -> y) -> (y -> r) -> (x -> r)
contramap f k = k . f
```

With `r = Bool`, an element of `Hom(X, Bool)` is a predicate on `X`:

```haskell
isPositive :: Int -> Bool
isPositive x = x > 0

stringLengthIsPositive :: String -> Bool
stringLengthIsPositive = isPositive . length
```

This idea appears in:

- predicate transformation,
- validation,
- continuation-passing style,
- backward program analysis.

---

## 3. Fixed-size records and vectors

In `Set`, if $A$ is a finite set with $n$ elements, then

$$
\mathrm{Hom}(A,X)\cong X^n.
$$

For example, if

$$
A=\{0,1,2\},
$$

then a function $A\to X$ is equivalent to a triple:

$$
\mathrm{Hom}(A,X)\cong X\times X\times X.
$$

In programming terms:

```text
FiniteIndex3 -> X
```

is essentially a fixed-length vector:

```text
(X, X, X)
```

This connection is used in:

- fixed-size arrays,
- records,
- representable functors,
- lookup tables,
- hardware descriptions.

---

## 4. Graph pattern matching

In the category of graphs, let $P$ be a small pattern graph. Then

$$
\mathrm{Hom}(P,G)
$$

is the set of graph homomorphisms from $P$ into a graph $G$.

Each homomorphism can be interpreted as an occurrence or match of the pattern inside $G$.

For example, if $P$ is a directed edge

$$
u\to v,
$$

then elements of $\mathrm{Hom}(P,G)$ correspond roughly to directed edges in $G$.

If $P$ is a triangle, $\mathrm{Hom}(P,G)$ describes triangle-shaped mappings into $G$.

This viewpoint appears in:

- graph databases,
- query matching,
- compiler pattern matching,
- model transformation,
- network analysis.

---

## 5. Database queries

A relational database can be modeled categorically. A query pattern $Q$ acts like a fixed object, and

$$
\mathrm{Hom}(Q,D)
$$

represents the possible matches of query $Q$ in database instance $D$.

For example, a query pattern might require:

```text
Person --worksAt--> Company
```

A homomorphism from that pattern into the database selects a person, a company, and a matching `worksAt` relation.

Applying a database transformation

$$
D\to D'
$$

maps query results through

$$
\mathrm{Hom}(Q,D)\to\mathrm{Hom}(Q,D').
$$

## 6. Syntax trees and interpreters

Suppose `Expr` is a free syntax structure generated by variables. A structure-preserving map

$$
\mathrm{Expr}\to A
$$

is an interpretation of expressions in a semantic domain $A$.

For free structures, one often has an isomorphism of the form

$$
\mathrm{Hom}(\mathrm{Free}(X),A)
\cong
\mathrm{Hom}(X,U(A)),
$$

where $U$ forgets the extra algebraic structure.

In programming terms, defining an interpreter for all syntax trees is equivalent to specifying what each primitive generator means.

Example:

```haskell
data Expr
  = Constant Int
  | Add Expr Expr
  | Multiply Expr Expr
```

An algebra homomorphism from `Expr` to integers gives an evaluator. A homomorphism into strings could give a pretty-printer.

This appears in:

- interpreters,
- compilers,
- abstract syntax trees,
- domain-specific languages,
- folds over algebraic data types.

## 7. Program states and reachability

Consider a category whose objects are program states and whose morphisms are valid executions.

Then

$$
\mathrm{Hom}(s,t)
$$

contains the executions that take state $s$ to state $t$.

Fixing the initial state $s$, the functor

$$
\mathrm{Hom}(s,-)
$$

describes how $s$ can reach other states.

In a simpler preorder model, there is at most one morphism:

$$
\mathrm{Hom}(s,t)=
\begin{cases}
\{\ast\}, & s\text{ can reach }t,\\
\varnothing, & \text{otherwise}.
\end{cases}
$$

This is relevant to:

- model checking,
- control-flow analysis,
- transition systems,
- security reachability,
- distributed-system traces.

---

## 8. APIs as objects and adapters as morphisms

Suppose objects are interfaces and morphisms are valid adapters between interfaces. Then

$$
\mathrm{Hom}(A,B)
$$

is the collection of ways to implement or adapt interface $A$ using interface $B$.

Fixing a required interface $A$,

$$
\mathrm{Hom}(A,-)
$$

asks: “How can each available implementation provide $A$?”

Composition corresponds to combining adapters:

```text
A adapter to B
B adapter to C
----------------
A adapter to C
```

This models ideas behind:

- dependency injection,
- interface adapters,
- middleware,
- protocol translation,
- compositional software architecture.

## Central programming example

The most direct example is:

$$
\boxed{\mathrm{Hom}(R,-)\;\text{is the Reader functor}\;(R\to-)}
$$

while

$$
\boxed{\mathrm{Hom}(-,R)\;\text{is a contravariant function-space functor}.}
$$

The first transforms outputs by postcomposition; the second transforms inputs by precomposition.

> Where I can the see construction of the homset shine through in the reader Haskell definition

The Hom-set construction appears **directly in the function type**:

```haskell
type Reader r a = r -> a
```

In the category **Hask**:

- objects are Haskell types,
- morphisms are Haskell functions,
- $\mathrm{Hom}(r,a)$ is the collection of functions from `r` to `a`.

So the Haskell type

```haskell
r -> a
```

is the programming representation of

$$
\mathrm{Hom}_{\mathbf{Hask}}(r,a).
$$

When `r` is fixed, this becomes the covariant Hom-functor

$$
\mathrm{Hom}(r,-):\mathbf{Hask}\to\mathbf{Hask}.
$$

## Object mapping

The Hom-functor sends an object $a$ to the Hom-set:

$$
a \longmapsto \mathrm{Hom}(r,a).
$$

In Haskell:

```haskell
a  ↦  Reader r a
   =  r -> a
```

For example:

```haskell
Reader Config String
```

means:

```haskell
Config -> String
```

Its values are morphisms from `Config` to `String`.

```haskell
getHost :: Config -> String
getHost config = config.host
```

Thus `getHost` is an element of:

$$
\mathrm{Hom}(\texttt{Config},\texttt{String}).
$$

The “set” part of Hom-set is not written explicitly. The type `Config -> String` represents the collection of all functions with that source and target.

## Morphism mapping

A functor must also map morphisms. Given:

```haskell
f :: a -> b
```

the Reader functor must produce:

```haskell
Reader r a -> Reader r b
```

Expanding the type synonym:

```haskell
(r -> a) -> (r -> b)
```

It does this by postcomposition:

```haskell
fmap :: (a -> b) -> (r -> a) -> (r -> b)
fmap f reader = f . reader
```

Categorically, a morphism

$$
f:a\to b
$$

induces a function between Hom-sets:

$$
\mathrm{Hom}(r,a)
\longrightarrow
\mathrm{Hom}(r,b)
$$

defined by

$$
g\longmapsto f\circ g.
$$

The correspondence is exact:

```haskell
reader :: r -> a
f      :: a -> b

f . reader :: r -> b
```

Diagrammatically:

$$
r \xrightarrow{\text{reader}} a \xrightarrow{f} b.
$$

## Concrete example

```haskell
data Config = Config
  { hostname :: String
  }

readHostname :: Reader Config String
readHostname config = hostname config

hostnameLength :: Reader Config Int
hostnameLength = fmap length readHostname
```

Expanding `fmap`:

```haskell
hostnameLength = length . readHostname
```

Here:

$$
\texttt{readHostname}
\in
\mathrm{Hom}(\texttt{Config},\texttt{String})
$$

and postcomposition with

$$
\texttt{length}:\texttt{String}\to\texttt{Int}
$$

produces

$$
\texttt{length}\circ\texttt{readHostname}
\in
\mathrm{Hom}(\texttt{Config},\texttt{Int}).
$$

## With the usual `newtype`

Reader is commonly defined as:

```haskell
newtype Reader r a = Reader
  { runReader :: r -> a
  }
```

The Hom-set is visible inside the constructor:

```haskell
runReader :: Reader r a -> (r -> a)
```

Ignoring the `newtype` wrapper:

$$
\texttt{Reader r a}
\cong
\mathrm{Hom}(r,a).
$$

Its `Functor` instance makes the postcomposition explicit:

```haskell
instance Functor (Reader r) where
  fmap f (Reader g) = Reader (f . g)
```

So the Hom-functor shines through in two places:

1. **The stored value**
   ```haskell
   r -> a
   ```
   is a morphism in $\mathrm{Hom}(r,a)$.

2. **The `Functor` action**
   ```haskell
   fmap f g = f . g
   ```
   maps between Hom-sets by postcomposition.

Strictly, ordinary Haskell has complications such as nontermination and `undefined`, so **Hask** is an informal approximation to the mathematical category of sets and total functions. That caveat does not change the structural correspondence shown above.

## Combining scenario-dependent calculations

The more important application is combining multiple calculations evaluated under the **same scenario**.

```haskell
portfolioValue :: ScenarioValue Dollars
portfolioValue scenario =
  bondValue scenario + stockValue scenario
```

Equivalently, using the Reader applicative:

```haskell
portfolioValue =
  (+) <$> bondValue <*> stockValue
```

```haskell
(<*>) :: (Scenario -> a -> b)
      -> (Scenario -> a)
      -> (Scenario -> b)

functions <*> values =
  \scenario -> functions scenario (values scenario)
```

The same `scenario` is supplied to every component. This is operationally important: the bond and stock values must be calculated under the same interest-rate, equity-price, and currency assumptions.

- the bond value from scenario 12,
- with the stock value from scenario 47.

The shared domain $S$ acts as a common coordinate system.

A risk pipeline might contain:

```haskell

  fmap (\value -> value - currentPortfolioValue)

  fmap (< minimumCapitalRatio) capitalRatio
```

The types correspond to:

$$
S\to\texttt{Dollars},
\qquad
S\to\texttt{Double},
\qquad
S\to\texttt{Bool}.
$$

The Hom-functor transports ordinary transformations:

$$
\texttt{Dollars}\to\texttt{Double}
$$

into transformations of whole scenario-indexed datasets:

$$
(S\to\texttt{Dollars})
\to
(S\to\texttt{Double}).
$$

No transformation needs to know how the scenarios are stored, enumerated, or generated.

## Why this is not merely “a function from configuration”

The construction gives several practical guarantees.

### Scenario alignment

Every value is indexed by the same fixed set $S$. Pointwise composition preserves that indexing.

### Modular calculations

A developer can write an ordinary transformation:

```haskell
calculateCapitalRatio :: Dollars -> Double
```

and automatically lift it to all scenarios:

```haskell
fmap calculateCapitalRatio
  :: ScenarioValue Dollars
  -> ScenarioValue Double
```

### Pipeline composition

Functoriality says:

$$
\operatorname{Hom}(S,g\circ f)
=
\operatorname{Hom}(S,g)\circ\operatorname{Hom}(S,f).
$$

In Haskell:

```haskell
fmap (g . f) values
==
fmap g (fmap f values)
```

Therefore, processing every scenario with one composed pipeline is equivalent to processing it in stages.

### Parallel execution

Although mathematically represented as $S\to X$, when $S$ is finite the value can be implemented as an array, distributed dataset, GPU tensor, or cluster computation:

$$
S\to X \cong X^{|S|}.
$$

Each scenario can be evaluated independently, while the Hom-functor describes the semantic structure of the computation.

## The general pattern

This same fixed-set Hom-functor appears whenever a system calculates values over a common index space:

$$
\operatorname{Hom}(S,X)=S\to X.
$$

Examples of $S$ include:

- market stress scenarios,
- geographic locations,
- sensor identifiers,
- experiment conditions,
- simulation worlds,
- user segments,
- time slots,
- possible system environments.

The key application is not merely storing $X$-values. It is maintaining a fixed, meaningful indexing context while ordinary computations $X\to Y$ are lifted automatically and safely to entire indexed datasets:

$$
X\to Y
\quad\leadsto\quad
(S\to X)\to(S\to Y).
$$

That is the practical content of the fixed-domain Hom-functor.

The **Hom-functor gives you `Functor` automatically**. The `Applicative` structure is not part of the Hom-functor definition itself, but for the Reader/Hom-functor it arises canonically from the fact that the same fixed input can be supplied to several computations.

For a fixed type $R$,

$$
\operatorname{Hom}(R,A) \cong R \to A.
$$

In Haskell:

```haskell
newtype Reader r a = Reader
  { runReader :: r -> a
```

## 1. What comes directly from the Hom-functor

Given a morphism

```haskell
f :: a -> b
```

postcomposition produces

```haskell
fmap f :: (r -> a) -> (r -> b)
```

with

```haskell
fmap f g = f . g
```

Categorically:

$$
\operatorname{Hom}(R,A)
\longrightarrow
\operatorname{Hom}(R,B),
\qquad
g \longmapsto f\circ g.
$$

That is precisely the Hom-functor action. Nothing beyond ordinary composition is needed.

## 2. Where `Applicative` adds something

The Reader `Applicative` is:

```haskell
instance Applicative (Reader r) where
  pure x = Reader (\_ -> x)

  Reader rf <*> Reader rx =
    Reader (\r -> rf r (rx r))
```

Removing the wrapper:

```haskell
pure :: a -> (r -> a)
pure x = const x

(<*>) :: (r -> a -> b)
      -> (r -> a)
      -> (r -> b)

rf <*> rx = \r -> rf r (rx r)
```

The central point is that both computations receive the **same** `r`:

```text
             r
            / \
           /   \
          v     v
   rf r :: a -> b
   rx r :: a
```

Their outputs are then combined:

```haskell
rf r (rx r) :: b
```

So Reader’s applicative behavior means:

> Run multiple computations in one common environment and combine their results pointwise.

## 3. A practical example

```haskell
data Config = Config

  , useTls   :: Bool

host = hostname

portNumber :: Config -> Int
portNumber = port

makeAddress :: String -> Int -> String
makeAddress h p = h ++ ":" ++ show p
```

```haskell
address :: Config -> String
```

Expanding it:

```haskell
address config =

    (host config)
```

$$
\texttt{host}\in\operatorname{Hom}(\texttt{Config},\texttt{String}),
$$

$$
\texttt{portNumber}\in\operatorname{Hom}(\texttt{Config},\texttt{Int}).
$$

The applicative structure combines them into:

$$
\texttt{address}
\in
\operatorname{Hom}(\texttt{Config},\texttt{String}).
$$

The common source object `Config` is preserved.

## 4. The categorical source: products

The key property is:

$$
\operatorname{Hom}(R,A\times B)
\cong
\operatorname{Hom}(R,A)
\times
\operatorname{Hom}(R,B).
$$

A function

$$
R\to A\times B
$$

is equivalent to a pair of functions

$$
(R\to A,\;R\to B).
$$

In Haskell:

```haskell
split
  :: (r -> (a, b))
  -> (r -> a, r -> b)

split f = (fst . f, snd . f)
```

and in the other direction:

```haskell
combine
  :: (r -> a)
  -> (r -> b)
  -> (r -> (a, b))

combine fa fb r = (fa r, fb r)
```

`Applicative` uses precisely this pointwise product structure:

```haskell
liftA2
  :: (a -> b -> c)
  -> (r -> a)
  -> (r -> b)
  -> (r -> c)

liftA2 combine fa fb =
  \r -> combine (fa r) (fb r)
```

Thus Reader can lift a multi-argument function:

$$
A\times B\to C
$$

into a function between environment-indexed values:

$$
(R\to A)\times(R\to B)
\longrightarrow
(R\to C).
$$

## 5. The diagonal map explains the shared environment

Categorically, the same environment is passed twice using the diagonal morphism:

$$
\Delta_R:R\to R\times R,
\qquad
r\mapsto(r,r).
$$

Suppose:

$$
f:R\to A,
\qquad
g:R\to B.
$$

First duplicate the environment:

$$
R\xrightarrow{\Delta_R}R\times R.
$$

Then run both functions:

$$
R\times R\xrightarrow{f\times g}A\times B.
$$

Then combine the outputs using some function:

$$
A\times B\xrightarrow{h}C.
$$

The complete composition is:

$$
R
\xrightarrow{\Delta_R}
R\times R
\xrightarrow{f\times g}
A\times B
\xrightarrow{h}
C.
$$

In Haskell:

```haskell
\r -> h (f r) (g r)
```

That is `liftA2`.

## 6. What `pure` means categorically

`pure` creates a Reader computation that ignores the environment:

```haskell
pure x = \_ -> x
```

This is a constant function:

$$
R\to A.
$$

Categorically, it factors through the terminal object $1$:

$$
R\to 1\to A.
$$

The first arrow is the unique map to the terminal object. The second selects the value $x$.

So:

- `pure` ignores the environment;
- `<*>` duplicates and shares the environment.

## 7. Is every Hom-functor automatically Applicative?

There are two levels to distinguish.

### External Hom-functor

In an arbitrary locally small category:

$$
\operatorname{Hom}(R,-):\mathcal C\to\mathbf{Set}
$$

is always a functor.

That alone does **not** automatically mean there is a Haskell-style `Applicative` endofunctor on $\mathcal C$.

### Reader in `Set` or Haskell

For functions:

$$
R\to -
$$

the ambient category has Cartesian products, diagonal maps, and constant functions. These provide the canonical `Applicative` structure.

Consequently, every Haskell functor representable in the form

```haskell
r -> a
```

has this canonical Reader-like applicative behavior.

## Bottom line

$$
\boxed{\text{Hom-functor} \Rightarrow \text{Functor via composition}}
$$

but:

$$
\boxed{
\text{Hom-functor}
+
\text{Cartesian product structure}
\Rightarrow
\text{Reader Applicative}
}
$$

So `Applicative` is **not part of the bare definition of a Hom-functor**. For the fixed-domain Hom-functor in `Set`/Haskell, however, it is a canonical additional structure rather than an unrelated invention. It expresses the ability to evaluate several morphisms from the same source object and combine their outputs.

That is a useful intuition, with one correction: **“program-construction side” is more accurate than “compiler side.”**

For fixed $R$, the Hom-functor

$$
\operatorname{Hom}(R,-)
$$

says that every function

$$
f:A\to B
$$

automatically induces another function

$$
\operatorname{Hom}(R,f):
(R\to A)\to(R\to B)
$$

defined by composition:

$$
g\mapsto f\circ g.
$$

In Haskell:

```haskell
fmap :: (a -> b) -> (r -> a) -> (r -> b)
fmap f g = f . g
```

## Construction versus execution

Suppose:

```haskell
readName :: Environment -> String
nameLength :: String -> Int
```

Then:

```haskell
readNameLength :: Environment -> Int
readNameLength = nameLength . readName
```

When `readNameLength` is constructed, no `Environment` is available or needed. We are merely connecting two functions:

```text
Environment -> String -> Int
```

Only later, when an environment is supplied,

```haskell
readNameLength env
```

does the actual computation occur:

```haskell
nameLength (readName env)
```

So the Hom-functor captures this distinction:

$$
\underbrace{A\to B}_{\text{ordinary transformation}}
\quad\leadsto\quad
\underbrace{(R\to A)\to(R\to B)}_{\text{transformation of programs awaiting }R}.
$$

It lets us manipulate and combine computations that still await their input.

## Why it is not specifically a compiler statement

Category theory does not distinguish compile time from runtime. The equation

```haskell
fmap f g = f . g
```

describes the meaning of the resulting function, independently of whether the compiler:

- inlines the composition,
- fuses the functions,
- allocates a closure,
- or executes them through some other representation.

The type checker can verify that the composition is valid before execution, and an optimizer may eliminate overhead. But those are consequences of the programming-language implementation, not part of the Hom-functor definition.

The categorical claim is more fundamental:

> Functions themselves can be inputs and outputs of other functions, and composition transforms a morphism $A\to B$ into a map between collections of morphisms $R\to A$ and $R\to B$.

## Where it appears in Haskell

The two parts of the Hom-functor appear in different places.

The object mapping appears in the type:

```haskell
Reader r a = r -> a
```

That is:

$$
A\mapsto\operatorname{Hom}(R,A).
$$

The morphism mapping appears in `fmap`:

```haskell
fmap f reader = f . reader
```

That is:

$$
f\mapsto(g\mapsto f\circ g).
$$

Therefore, a sharper version of your statement is:

> The Reader Hom-functor says that we can transform and compose programs that await a fixed input, without supplying that input yet; execution happens only when the input is eventually provided.

`Applicative` extends this idea from composing a single output transformation to assembling several computations that all await the same input:

```haskell
makeResult <$> readName <*> readAge
```

This constructs:

```haskell
\env -> makeResult (readName env) (readAge env)
```

Again, the program is assembled first; the shared environment is supplied later.
